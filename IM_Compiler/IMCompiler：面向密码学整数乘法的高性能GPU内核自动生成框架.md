随着数字数据的不断增长和数据安全风险的增加，隐私保护计算技术在现代计算环境中变得尤为重要。加密大整数乘法是许多隐私保护计算技术中的核心计算操作，尤其在如RSA、ElGamal和Paillier等加密系统中，要求使用大于2048位的密钥以确保足够的安全性。**大整数乘法的计算量巨大，且随着密钥位数的增加，计算量也呈指数级增长，由于其复杂性和对特定应用定制实现的需求，给GPU加速带来了挑战。**

今天要分享的论文是**《A Compiler-Like Framework for Optimizing Cryptographic Big Integer Multiplication on GPUs》**，发表于2024年第57届IEEE/ACM微架构国际研讨会**（MICRO）**。该论文的作者团队来自山东大学、香港理工大学和蚂蚁集团。**该论文提出了一种名为 IMCompiler 的类编译器框架，用于自动生成优化的GPU内核，以加速密码学中的大整数乘法运算。**实验表明，**IMCompiler** 相比广泛使用的基线实现实现了 4.47倍 的加速，相比Nvidia官方库 CGBN 也有 1.42倍 的性能提升，且在大整数和高性能GPU上表现更优。

![[zhihu/images/ef/6c/ef6cef01263e5dd3a6049b5a4ee29ff7.jpg]]

## **一、研究背景**

### **（1）研究背景**

-   随着数据安全和隐私保护需求的增长，隐私计算技术（如安全多方计算、同态加密、零知识证明等）变得日益重要。这些技术的核心运算之一是大整数乘法，其计算复杂度高，且常涉及2048位以上的密钥，单次操作就包含数千次32位整数乘法。
-   GPU因其高并行计算能力成为理想的加速平台，但其架构复杂，不同GPU型号、不同密码系统、不同整数长度和乘法变种（如平方、乘高、乘低）都需要不同的优化策略。现有的加速方法往往依赖于手动优化，针对不同的硬件架构和应用场景设计特定的优化策略，这一过程非常复杂且劳动密集。

### **（2）关键挑战/现有不足**

-   并行化设计空间复杂：需平衡片上资源、通信开销、并行度、负载均衡和内存访问模式。
-   参数多样性：不同密码系统、密钥长度、乘法变种（如平方、乘高mul\_high、乘低mul\_low）需定制实现。
-   手工优化不可扩展：为每种情况手动优化GPU内核工作量巨大，难以适应多样化的部署场景。
-   现有库局限性：如Nvidia的CGBN虽高效，但依赖于特定GPU架构，且未充分利用乘法变种的优化潜力。

## **二、核心思想和方法**

### **（1）整体设计**

为便于自动代码生成，IMCompiler采用了类编译器设计，如图1所示。具有前端-中间表示（IR）-后端架构，以将架构特定优化与高级参数解耦。输入为应用程序的源代码，其中每个大整数乘法被定义为函数调用，参数指定位长和变体。这种设计选择与大多数密码学应用的结构一致，在这些应用中，大整数乘法通常通过函数调用来实现。此外，为每个操作选择最优变体通常较为简单，因为大多数密码系统会在其文档中对此进行指定。

对于每个函数调用，前端提取高级参数，然后据此生成优化的IR代码。IR代码随后由后端转换为参数化内核，该内核旨在便于跨各种GPU架构进行适配。这些优化后的内核随后被集成到源代码中，取代原始的大整数乘法函数。最后，调用标准GPU编译器来编译代码。

![[zhihu/images/b8/60/b860d25ad5bdf8c11700ae8948da6023.jpg|图1 IMCompiler：类编译器的前端-中间表示-后端设计]]

### **（2）IR：**

IR的设计是IMCompiler实现解耦的关键，其核心是分段整数乘法算法。

-   分段：如图2所示，每个大整数（A,B）被划分为多个长度为Ns的段（Segment）。Ns是一个超参数，由GPU型号决定，与具体的整数位长N无关。
-   计算：整个大整数乘法 C=A∗ B被转化为所有可能的分段对 (segA\[i\], segB\[j\]) 的乘积之和。每个分段对的乘法由 UNIT\_MUL(segA\[i\], segB\[j\]) 完成，产生一个2Ns位的结果，这些部分积最终被累加到结果 C 的相应段中。

![[zhihu/images/ea/6e/ea6ecf001483abf441c6ffe7c0df552e.jpg|图2 分段整数乘法示意图]]

算法1详细描述了IR的执行过程。每个N位整数乘法由包含NT个线程的线程组计算。该线程组通过双重循环串行遍历段对，其中外层循环遍历乘积的段，内层循环累加由UNIT\_MUL计算的部分结果。这种迭代顺序避免了关于乘积段的昂贵读-修改-写操作和进位传播。在UNIT\_MUL中，一个段对（即两个Ns位整数）由NT个线程并行相乘。因此，对于m个N位整数乘法，会启动m×NT个线程，该值与位长N无关。

分段整数乘法算法不仅允许战略性地选择Ns以进行性能优化，还将并行整数乘法的所有实现细节封装在UNIT MUL中。其余指令仅作为支持代码。这种将并行化细节与高级参数的解耦，使得不同位长和变体的整数乘法能够直接转换为一系列UNIT MUL调用。它允许前端独立管理各种高级参数，而无需处理后端负责的并行化复杂性。

![[zhihu/images/c9/70/c9708c8df7da12e9a5d3d438df119c12.jpg]]

### **（3）使用计算图优化后端：**

**计算图建模:**

在GPU上并行化整数乘法面临着显著挑战，这是由于固有的数据依赖性、工作负载不平衡以及不规则的内存访问模式所致。虽然优化单个因素看似简单，但可能会加剧其他问题。通过公式化建模来分析这些因素之间复杂的相互作用并不直观。为此，本节引入计算图以直观地描述这些相互作用。

计算图示例如图3所示：每个元素代表一条宽乘法指令，蓝色线条表示加法操作。沿对角线的加法操作表示高32位及其相关进位的传播。黄色封闭图形勾勒出每个线程的工作负载。计算图直观地揭示了优化时需要权衡的多个性能因素：

-   工作负载：黄色形状的面积。
-   通信开销：蓝色对角线的数量与模式（规则与否）。
-   Warp发散：黄色形状的大小和形状是否一致。
-   片上资源使用：缓存数据所需寄存器或共享内存的量。

![[zhihu/images/39/4c/394cec45594c8b2f592813dc9e84f524.jpg|图3 计算图示例]]

**二维并行化策略：**

论文使用计算图分析了多种现有策略的缺陷，并提出了更优的二维并行化策略。

-   ：如图4a所示，将每个线程分配给一个宽乘法指令（即 ）会导致片上内存使用量和通信成本过高。此外，每个线程的工作负载不足以分摊线程初始化成本。
-   ：如图4b所示将每个线程分配给一个字 可减少通信开销并确保可行的每线程工作负载。然而，这会导致显著的warp分化。一些线程执行单个宽乘法指令，而另一些线程执行Ns个宽乘法指令。
-   segC：图4c展示了易并行算法，其中每个线程计算一个segC。虽然该方法消除了通信开销和warp分化，但却给单个线程带来了过重负担，显著降低了并行度并阻碍了循环展开。
-   许多先前的实现采用图4d所示的一维并行化策略，其中每个线程处理计算图中一行或几行的计算。尽管这种方法显著改善了上述因素之间的平衡，但计算图表明它可能不是最优解决方案。
-   二维并行化策略图4e，其中每个字的计算分布在多个线程中，每个线程也负责计算多个字的部分积。对于矩形尺寸(Nb1)和(Nb2)，每个线程的工作负载为Nb1×Nb2个宽乘法指令，通信成本约为Nb1+Nb2。相比一维策略，二维策略在**工作负载、通信开销、并行度和资源使用**之间取得了更好的平衡。

![[zhihu/images/d0/68/d0682f0e1b2fd7fb57cccc8159f95b7f.jpg|图4 并行化策略分析与计算图]]

**并行化kernel：**

算法2展示了并行整数乘法 GPU 内核的简化实现，该实现采用了二维并行化策略。正方形的边长预先确定为Nb。因此，分配给每边的线程数为 TPS = Ns/Nb，并且由 NT = TPS × TPS个线程并行地对一个段对进行乘法运算。每个线程最初处理其指定的工作负载，该工作负载由N²b个字的部分积组成。迭代顺序也遵循Comba方法，以减少片上资源使用并避免频繁的进位传播。之后，同一线程组内的NT个线程通过共享内存交换数据，然后累加每个字的部分积以生成最终结果。

![[zhihu/images/57/c4/57c435d404c2e85458ac96f80d9a1e66.jpg]]

**软硬件协同优化：**

-   索引转置：在累积前对数据进行转置。转置后，原本连续的数据被 stride 访问，使得每个线程负责累积不同字的不同部分，确保了同一Warp内线程的工作量高度一致，消除了发散。
-   惰性进位：在局部计算阶段，允许中间结果暂时大于基值，将进位 propagation 延迟到最后的全局累积阶段。这大大减少了计算过程中的通信同步次数。
-   定制缓存策略：输入数据缓存在寄存器中，而非共享内存，寄存器延迟更低，且避免了共享内存的bank conflict。中间结果使用共享内存进行线程间交换，共享内存更适合此类随机访问，将输入（寄存器）和中间结果（共享内存）分开存放，有助于平衡不同片上资源的使用，提高GPU的占用率。

## **三、实验与评估**

### **（1）实验设置**

**软件环境：**

-   NVIDIA GPU：Ubuntu 18.04, CUDA Driver 530.30.02, CUDA Runtime 12.1。
-   AMD GPU：Ubuntu 20.04, ROCm Toolkit 5.0。

**硬件环境：**

-   NVIDIA H100 PCIe 80GB：高端数据中心GPU。
-   NVIDIA RTX 4090：高性能消费级GPU。
-   NVIDIA Jetson AGX Xavier：嵌入式GPU平台。
-   AMD Radeon 6900XT：代表非NVIDIA的GPU架构。
-   CPU参考：Intel 13900KF CPU，用于运行GMP库作为性能参考。

**基准测试：**

-   BASE：朴素的并行方法。每个线程独立处理一个完整的大整数乘法。此方法仅利用了操作间的并行性，未利用操作内的并行性，作为性能比较的基线。
-   CGBN：由NVIDIA官方发布的基于协作组的高精度整数运算库。它代表了当前最先进的GPU大整数乘法实现。
-   NTT：基于数论变换的大整数乘法实现。对于非常大的整数，NTT在理论上有更优的时间复杂度。
-   GMP：在CPU上运行的GNU多精度运算库。作为广泛使用的CPU参考实现，用于展示GPU加速的整体效益。

### **四、总结与贡献**

本文介绍了IMCompiler，这是一个类编译器框架，旨在为密码学应用中使用的各种整数乘法任务自动生成GPU内核。IMCompiler采用前端-中间表示-后端结构，将特定于架构的优化与高级参数解耦，能够为不同位长和特殊变体的整数乘法自动生成高效的GPU内核。在提出的计算图的指导下，IMCompiler实施了一系列优化措施，使算法与硬件相匹配，包括二维并行化、定制缓存策略、索引转置和延迟进位。全面评估表明，与BASE和NTT相比，IMCompiler的吞吐量分别提高了4.47倍和142倍。与CGBN相比，对于2048位密钥的密码系统，IMCompiler的吞吐量提高了1.42倍。随着密钥尺寸的增大和GPU性能的提高，其性能进一步提升。
